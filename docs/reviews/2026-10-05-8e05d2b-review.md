## 2. New or additional findings, ranked by severity

### N1 — Medium: room-noise findings describe unrecorded gaps as continuously observed noise

**Locations:** [js/noise.js:163](https://github.com/kirdhsali/Snore/blob/8e05d2b18078bbbae589e7a19572f352cb844294/js/noise.js#L163), `:174–182`, `:196–199`, `:242–259`; consumers `js/app.js:661–669`, `:717`, and `scripts/evaluate.js`. Introduced with the room-noise feature after 1.12.

**Verified reproduction:** pass `Noise.summarize()` 52 observed minute records: 20 quiet minutes, 6 raised minutes, a missing hour, 6 raised minutes, then 20 quiet minutes. Raised background is −81 dBFS versus −89; bands ≥500 Hz rise 8 dB. The observation timestamps jump from minute 25 to minute 86.

**Actual:** the summarizer joins the twelve raised observations into `start:1200, end:5520` and `describe()` says both:

> 0:20–1:32: a steady sound in the middle and high pitches …
>
> 0:20–1:32: the room was 8 dB louder than at its quietest; quiet snores could be missed then.

That is a **72-minute continuous finding containing 60 unrecorded minutes**. The source loops over neighboring array entries, not neighboring clock minutes. Dropping records whose background is null can create the same discontinuity. Tone windows also count ten records as ten consecutive minutes. The collector's existing “no minutes are made up during an interruption” test passes because it tests the profile, not this summarization stage.

**Expected:** missing time must stay unknown. Split analysis at timestamp discontinuities and respect partial/invalid observations; do not infer a continuous device/noise state through the gap. With the existing ten-minute minimum, the two six-minute stretches need not produce a finding at all. The heatmap already marks gaps; the prose must agree with it.

**Suggested fix:** make smoothing, runs and tone windows time-aware; supply coverage/gaps where minute data alone is insufficient. Say “of the observed recording” rather than “of the night” when coverage is incomplete. Add a summarizer regression using the fixture above, plus missing-background and partial-minute cases. No detector threshold/counting change is needed.

**Impact:** misleading app, shared-HTML and CLI descriptions of the room. I did not observe an effect on snore counts or audio retention.

### N2 — Medium: alternative-rule counts can keep rattles whose supporting snore was removed

**Locations:** [scripts/evaluate.js:183](https://github.com/kirdhsali/Snore/blob/8e05d2b18078bbbae589e7a19572f352cb844294/scripts/evaluate.js#L183), `:204–220`, `:241–250`, `:269–278`; background event export `js/report-format.js:158–181`.

**Verified reproduction:** create two otherwise eligible choppy sounds at 2 and 6 s, and a smooth anchor at 10 s. The choppy sounds have four peaks, breath rise 8 dB and one-second pre-rise 10 dB; the anchor has one peak, breath rise 4 dB and pre-rise 7 dB. The existing auto rules (breath 3, pre-rise 6) accept all three: the anchor rescues both rattles.

Tighten breath to 6 dB. `stricterBreath()` reports **2 confirmed**, whereas `reevaluate()` through the actual classification/rhythm gate reports **0**. Tighten pre-rise above 7 dB and the same discrepancy occurs with `preRiseVariant()` — **2 versus 0**. With no independently accepted anchor, those two rescued sounds cannot legitimately anchor each other under the approved rule.

**Cause:** both shortcuts turn surviving stored sounds into `isSnore:true` and only rerun confirmation. They do not redo rhythm rescue. The source comments admit this approximation, but the command's output presents precise “confirmed” counts/rates without that limitation. Background exports omit the full classification/rhythm features needed to reproduce the real decision path. Relaxing pre-rise has another limitation: eligible choppy candidates among the set-aside sounds are explicitly excluded, so it can undercount as well.

**Expected:** a candidate-rules count should reproduce the candidate rule's anchor/rescue behavior, or clearly state that it is an estimate and cannot support an exact comparison.

**Suggested fix:** preserve enough background candidate features and rerun the shared classification/rhythm/confirmation pipeline. Until then, label these tables **approximate**, explain the orphan-rescue/omitted-candidate limitation and avoid presenting them as exact evidence for choosing defaults. Add the three-event fixture above for both helpers. Keep owner-approved defaults unchanged.

**Impact:** misleading offline comparisons when deciding future rules. The live count and the main full-feature `reevaluate()` path are not shown broken by this reproduction; R3/R9's original fixes remain valid.

### N3 — Low: old files with no breath measurements produce false zeroes in background comparisons

**Locations:** [scripts/evaluate.js:187](https://github.com/kirdhsali/Snore/blob/8e05d2b18078bbbae589e7a19572f352cb844294/scripts/evaluate.js#L187), `:241–250`.

**Reproduction:** `node scripts/evaluate.js tests/fixtures/v1.8-report.json`.

**Actual:** the file loads; the main comparison correctly warns `missing: breathRiseDb (breath-noise rule cannot be checked)` and preserves two confirmed snores. Farther down, the auto comparison nevertheless prints **0 at 3, 4.5 and 6 dB**. `stricterBreath()` rejects every sound with an absent value.

**Expected:** “not evaluable: breath measurements absent”, not a numerical result implying every sound would fail. The existing compatibility test verifies that the command works and warns, but not this background-table conclusion.

**Suggested fix:** check feature coverage per background test before evaluating each variant; report unavailable/partial evidence explicitly. Do not treat unknown measurements as zero or failed measurements.

**Impact:** misleading analysis of older data; no legacy-file parsing failure and no live recording defect. The existing top-level warning reduces the severity.

## 3. Privacy, retention, memory and data compatibility

**No automatic night-data upload found.** Source inspection of the application found no audio/report transport, analytics client, fetch/XHR, beacon or WebSocket path. Browser request observation during start, interruption, recovery, Stop and report download saw local assets, a local worklet Blob and an external **Google Fonts stylesheet GET with no body**; the font request failed in this environment. Nothing in that observed session sent audio or report data. User-initiated OS sharing is a separate, intentional export. This is evidence of local processing, not a promise that the page makes no external requests.

**Retention policy is implemented as documented.** The main detector keeps short accepted/snore-like clips, including “possible” events. Knock keeps no clips. Auto and High retain samples of their accepted sounds that do not overlap main detections; High additionally requires breath rise in [3,6) dB. At Stop, late main matches are discarded and the final caps are applied. Therefore test clips can include sounds the headline detector rejected — this is the recorded owner decision, not an undisclosed full-night recording. False positives and surrounding pre/post-roll audio remain possible.

I ran a **one-hour synthetic stream** by repeating the quiet-bedroom fixture through the real controller/four detectors at 16 kHz. It completed in 9.32 s of accelerated Node processing. The result contained 60 auto clips, 6 High clips and 0 knock clips; every retained test clip satisfied its eligibility check and did not overlap a main event. Observed reservoir peaks were 114 auto and 6 High, below 120/60. A smaller High cap of 3 ended with 1 clip: the reservoir is allowed to underfill after late main matches are removed. I checked the combined test WAV's samples against the retained PCM and the number of non-null JSON WAV positions. The WAV was 1,669,976 bytes, compact JSON 161,572 bytes, and the profile had 60 minutes. The default High cap was not saturated by this fixture; its shared cap implementation and smaller-cap behavior were inspected separately. These are retention/export checks, **not an iPhone endurance test**.

**R6 remains material.** The 1,500-clip limit is a count limit; duration/rate affect bytes, and metadata for all four detectors grows throughout the night. Clips from a 44.1 kHz input use 8,820 Hz, not exactly 8,000 Hz (`js/detector.js:384–385`). WAV creation allocates a complete output buffer (`js/wav.js:28–54`) and the app then wraps it in a Blob (`js/app.js:851–861`). In an independent Node capacity fixture using 1,501 accepted four-second PCM clips at 8,820 Hz:

- 1,500 clips survived the cap, holding **105.84 MB** of PCM;
- the WAV allocated **116.42 MB**, including inter-clip silence;
- the Blob was another **116.42 MB**;
- measured ArrayBuffer memory rose to **338.82 MB** (~323 MiB), before other app/browser costs; RSS was ~362.7 MiB;
- WAV construction took ~215 ms on this desktop runtime.

This verifies a substantial allocation path; it does **not** prove a particular iPhone will crash or use identical memory. A byte budget, bounded metadata/retention strategy and measured export peak are still needed before claiming long-night reliability. The new test reservoirs add bounded audio but do not fix the existing main-clip/export problem.

**Compatibility:** v1.8/schema 1, v1.9/schema 1 and the new schema 2 export all read successfully. v1.9 demo: 16→16 confirmed; v1.8: 2→2, with the missing-feature warning and N3 caveat. The report-format tests verify preservation of previous fields, newer ignored-event features, noise, time zone, pre-rise values and shadow WAV positions. Schema 2 additions are optional and the current reader tolerates older shapes. This is compatibility for the evaluator, **not a complete saved-night restore format**: the exported/read object does not reconstruct the full runtime record, stats object, every configuration field or raw clips. Feature/time rounding also makes offline boundary decisions approximate; HANDOVER already records this limitation.

**HTML handling:** I found no currently reachable user-controlled HTML injection path. Generated noise findings are escaped in the app and shared report; the share test includes `<50> Hz & more` and verifies escaping/script-free output. Numeric SVG inputs originate inside the current app. This should be reassessed before accepting arbitrary imported JSON or user names: `fromReport()` validates only a small part of the shape, not a hostile-input boundary.

## 4. Readiness and the earlier architecture/workflow recommendations

**Nightly personal use on an iPhone:** suitable for continued personal experimentation with the screen kept awake and manual export, but **not yet demonstrated dependable for an unattended night**. My tests do not establish microphone continuity across a real call, Siri, screen locking, foreground/background changes, power-saving behavior or memory pressure. A successful demo and synthetic hour cannot supply that evidence. A reload/crash still loses the in-memory night.

The handover mentions six owner recordings on earlier versions; their private evidence was not available to me. That useful experience does not replace a controlled overnight acceptance test of the **1.22 four-detector configuration**, particularly its interruption/recovery behavior. I have not treated it as such.

**Architecture: partly ready, without a need for more folders just to increase folder count.** The split into pure detector/stats/WAV/noise/report modules, browser recorder and UI is a sensible base for this app. More subfolders would not fix the substantive boundary issues. I would keep the working functionality and make the next expansion steps explicit:

1. **Before saved nights/history:** fix C4; define a versioned persisted night/event/clip schema, stable identity and migrations; implement a durable on-device store behind `night-store.js`; checkpoint incrementally and recover incomplete nights. Test reload/crash, quota failure, delete and clip/event consistency. The current in-memory store/interface is not persistence or recovery.
2. **Before larger unattended use:** set a clip byte budget, bound or compact event metadata, reduce export peak allocation, and measure real-phone CPU/battery/memory with four detectors over a full night. Add recovery so pressure does not erase all prior progress. Decide the C6/gap-edge time contract and episode policy before building cross-night analytics on it.
3. **Before native iPhone work:** retain the pure detection/report logic, but separate the browser capture/lifecycle implementation from the recording controller behind an explicit adapter. `createRecorder({env})` helps testing, but currently assumes Web Audio nodes, streams, DOM visibility and browser wake locks. Prototype a real native recording/lifecycle path if locked-screen recording is a goal; do not assume a wrapped web page resolves it.
4. **Before users/cloud sync:** decide whether “users” means local profiles or accounts with a backend. Upload/sync would change the current privacy promise and requires an explicit owner decision, data ownership/deletion rules and a new security review. It is not necessary for local saved nights.

**Browser/device coverage: still unresolved.** The automated browser evidence is Chromium; the recorder unit fake exercises the ScriptProcessor fallback but cannot establish its behavior on a real device. Add a controlled iPhone night, interruptions, wake-lock refusal/recovery, playback, exports and recovery after reload. Use additional browser automation to catch web regressions, while retaining physical-phone acceptance testing.

**Workflow permissions/gating: original minimum fixed; stronger guarantee still deferred.** I read the pinned workflow files and independently queried the current read-only GitHub metadata:

- `.github/workflows/ci.yml:5–20` uses `contents: read` and runs unit tests, lint and Chromium E2E.
- `pages.yml:17–30` and `release.yml:11–22` gate their publish/tag jobs on unit tests and syntax checks of the same revision. They do **not** depend on completion of the full CI browser/lint job.
- Permissions remain workflow-wide for Pages writes/OIDC and release contents writes. Pages listens to all branch pushes with one `pages` concurrency group (`pages.yml:5–14`); off-main runs can contend with a main deployment before per-job branch conditions are applied. Actions use version tags rather than immutable SHAs. These match the recorded deferred hardening items; I did not change them or trigger a race.
- The live [Protect main ruleset](https://github.com/kirdhsali/Snore/rules/24320267) is active: PR required, `CI tests` required, deletion/non-fast-forward blocked, no bypass actors. It requires zero approvals and does not require the branch to be up to date (`strict_required_status_checks_policy:false`). These are current settings, not immutable properties of the reviewed commit.
- For main `687b1f7`, GitHub reports successful [CI](https://github.com/kirdhsali/Snore/actions/runs/37309563309), [Pages](https://github.com/kirdhsali/Snore/actions/runs/37309563442) and [release](https://github.com/kirdhsali/Snore/actions/runs/37309563285). Before wider release, gate the exact published revision/artifact on the complete required checks, limit deploy trigger/concurrency to the intended branch, and scope write permissions to the jobs that need them. These are release-engineering improvements, not reasons to change detection defaults.
